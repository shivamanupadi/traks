# Security

Traks handles other people's traffic data, so reports are taken seriously and
answered quickly.

## Reporting a vulnerability

Please do not open a public issue for anything security-related. Use GitHub's
private reporting instead:

**[Report a vulnerability](https://github.com/shivamanupadi/traks/security/advisories/new)**

Include what you found, how to reproduce it, and what you think the impact is.
You will get an acknowledgement within three days and a fix or a clear answer
within two weeks for anything confirmed. Credit is given in the release notes
unless you prefer otherwise.

## Scope

- The platform that runs in users' Cloudflare accounts: `apps/platform`
  (collect Worker, api Worker, dashboard) and `packages/tracker` (`t.js`).
- The traks.dev deploy wizard and its backend: `apps/home`.
- Release tooling under `installer/`.

Cloudflare's own services are out of scope; report those to Cloudflare.

## What Traks stores, for context

- User instances store only what the dashboard shows: visitor counts from a
  daily-rotating hash, pages, referrers, geography. No IP addresses, no
  cookies, no cross-day identifiers.
- traks.dev stores nothing about instances. The wizard rediscovers them from
  the user's own Cloudflare account on each sign-in; a run's progress lives in
  a Durable Object that wipes itself after a day. Tokens are used for the
  request they arrive in and never persisted.

## Trust boundaries in an instance

Everything below lives in the instance owner's own Cloudflare account. None of
it is reachable from traks.dev after the install finishes.

- **The catalog token is stored in three places.** The wizard asks for one
  Cloudflare API token with R2 Storage Write, R2 Data Catalog Write and R2 SQL
  Read. It becomes the Pipelines sink credential (needs write to commit
  Iceberg files), the catalog's service credential (compaction and snapshot
  expiration need write), and the `R2_SQL_TOKEN` secret on the dashboard
  Worker, which only ever runs read-only R2 SQL queries with it. The dashboard
  Worker is the internet-facing surface (login, dashboard, MCP), so a
  compromise there would expose a token that can write and delete objects in
  the buckets it is scoped to and drop catalog tables, not only read the
  analytics table. Cloudflare has accepted read-only tokens for R2 SQL since
  July 2026; Traks keeps a single token to keep the install to one paste and
  documents the boundary here instead.
- **Reduce the blast radius when creating the token.** The wizard's pre-filled
  link scopes the token to your account. In Cloudflare's token editor you can
  narrow the R2 permissions further to the single `<instance>-events` bucket
  before creating it; the install works the same.
- **Rotate it without reinstalling.** Create a new token, then update the
  three copies: the dashboard secret with
  `npx wrangler secret put R2_SQL_TOKEN --name <instance>-api`, the sink via
  the Pipelines dashboard, and the catalog service credential under R2 Data
  Catalog settings. Revoke the old token last.
- **The site key is public by design.** It ships in the page's `t.js` tag.
  Events are tied to a site by the request `Origin` matching the registered
  domain, not by the key, and a per-site-key burst limit bounds abuse.
- **Visitor identity cannot be reversed.** Visitor ids are
  `HMAC(VISITOR_HASH_SECRET + date, ip + ua + siteKey)`; the secret is
  generated by the wizard, stored only as a Worker secret on the collect
  Worker, and never leaves the account.
